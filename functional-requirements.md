# Функциональные требования 

## Типы пользователей:
1.	[организатор](#1-организатор)
2.	[судья](#2-судья)
3.	[участник](#3-участник)
4.	[зритель](#4-незарегистрированный-пользователь-гость)

*Пользователь может совмещать роли Участника, Судьи и Организатора.*


## 1. ОРГАНИЗАТОР
### Управление фестивалями
**Организатор должен:**\
•	Заполнить обязательные поля при создании фестиваля: название, дата проведения, адрес/место проведения;\
•	Добавить хотя бы одну категорию конкурса перед публикацией фестиваля;\
•	Назначить форму оценивания каждой категории.\
\
**Организатор должен иметь возможность:**\
•	Добавить описание фестиваля (текстовое поле, необязательное);\
•	Редактировать информацию о фестивале (название, дату, адрес, описание) в любой момент до начала мероприятия;\
•	Создать фестиваль на основе существующего с копированием обязательных полей и настроек с возможностью изменения категорий;\
•	Просматривать списки своих фестивалей с возможностью фильтрации по дате.

**Система должна:**\
•	Присвоить каждому созданному фестивалю уникальный идентификатор (Festival_ID).

### Управление категориями
*(В рамках MVP система не поддерживает вложенность категорий, форма оценивания категории едина для всех судей)*

**Организатор должен:**\
•	Выбрать тип категории при её создании: Соло, Дуэт или Команда. Тип категории определяет структуру данных об участниках;\
•	Назначить форму оценивания каждой категории (из своих или из публично доступных шаблонов, созданных другими организаторами);\
•	Выбрать вариант агрегации для получения итогового результата по оценкам судей. Доступные результаты: «Среднее арифметическое», «Сумма»;\
•	При добавлении номеров в категорию заполнить обязательные поля исходя из типа формы:
* Для номинации «Соло»: ФИО одного участника
* Для номинации «Дуэт»: ФИО двух участников
* Для номинации «Команда»: название команды

**Организатор должен иметь возможность:**\
•	Добавить название категории;\
•	Добавить название номера и перечислить состав участников команды;\
•	Применить одну форму оценивания ко всем категориям фестиваля;\
•	Заменить форму оценивания в конкретной категории;\
•	Редактировать название категории и привязанную форму до момента начала оценивания судьями;\
•	Добавлять новые категории;\
•	Удалять пустые категории;\
•	Указать формат подсчёта результатов категории по судьям - среднее арифметическое или сумма оценок *(по умолчанию должно использоваться среднее арифметическое)*;\
•	Редактировать состав участников в категории (добавлять/удалять).\
\
**Система должна:**\
•	Хранить данные участников без требования регистрации в системе;\
•	Проверять заполненность всех необходимых полей в форме при добавлении номеров в категорию;\
•	Хранить выступление в привязке к категории;\
•	Отображать судьям только непустые категории .

### Управление системами (шаблонами) оценивания
**Организатор должен иметь возможность:**\
•	Создать систему оценивания как независимый объект, не привязанный к конкретному фестивалю;\
•	Использовать функцию «Создать на основе» для клонирования существующей системы (своей или публичной) с последующим редактированием.;\
•	Фильтровать системы по названию и по жанру (например, только формы для танцев, только для гимнастики);\
•	Сделать свою систему публичной (доступной другим организаторам) или приватной (только для личного использования);\
•	Редактировать параметры системы: название, жанр, критерии, формулу расчёта, способы отображения UI-элементов, наличие поля для комментария судьи;\
•	Просматривать свои системы и редактировать их независимо от фестиваля.

**Система должна:**\
•	Присвоить каждой системе уникальный идентификатор (Form_ID);\
•	Хранить настройки системы в отдельной таблице с возможностью переиспользования на разных фестивалях;\
•	При клонировании системы создать независимую копию: изменения в оригинале не влияют на клон и наоборот;\
•	Отображать список доступных систем с фильтрацией по типу (свои, публичные, по жанру);\
•	Контролировать права доступа: организатор может редактировать только свои системы;\
•	Контролировать права доступа пользователей к приватным системам и их отображение.

### Мониторинг и протоколы
**Организатор должен иметь возможность:**\
•	Просмотреть итоговый протокол автоматически после закрытия формы и завершения оценивания;\
•	Экспортировать протокол в форматах PDF, Excel, CSV;\
•	Настроить уровень доступа к протоколу: полный (все оценки и детализация), только итоговые баллы и места;\
•	Опубликовать протокол для участников и гостей или оставить приватным.
\
**Система должна:**\
•	Автоматически рассчитать итоговые баллы по формуле, заданной в системе оценивания, после закрытия формы;\
•	Ранжировать участников по итоговому баллу в рамках каждой категории;\
•	Сгенерировать протокол с указанием места, ФИО/названия команды, названия номера, итогового балла и детализации по критериям и баллам каждого судьи.\

### Настройка разбалловки и маппинга оценок
**Организатор должен:**\
•	Задать названия опций, начальное значение и шаг численного эквивалента опциям для категориально упорядоченных критериев формы;\
•	Указать минимальное, максимальное значения и шаг для численных критериев формы.

**Организатор должен иметь возможность:**\
•	Изменить параметры разбалловки критерия;\
•	Изменить отображаемое название категориально упорядоченного критерия в форме судьи без изменения его идентификатора и числового значения в системе.

**Система должна:**
•	Хранить маппинг (численный эквивалент) для каждого варианта оценки в рамках категориального упорядоченного критерия;\
•	Запрещать сохранение критерия, если хотя бы одному варианту оценки не присвоено числовое значение или оно присвоено с ошибкой;\
•	Использовать уникальный идентификатор критерия (criterion_id) во всех внутренних расчётах и формулах, а не его текстовое название.

### Выбор и настройка формулы расчёта  
**Организатор должен:**\
•	Выбрать вариант формулы для получения итогового балла после заполнения судьей формы оценивания или написать ее сам. Доступные встроенные варианты: «Сумма», «Взвешенная сумма».

**Организатор должен иметь возможность:**\
•	В режиме шаблона «Взвешенная сумма» вручную ввести весовой коэффициент для каждого критерия;\
•	Изменить вариант подсчета баллов по формуле;\
•	Собрать пользовательскую формулу, последовательно выбирая элементы из трёх выпадающих списков: критерии, математические операции и функции агрегации;\
•	Выбрать в блоке «Критерии» любой из критериев системы оценивания (критерии не должны повторяться);\
•	Выбрать в блоке «Математические операции» — <ins>+, -, ×, ÷, (, )</ins>;\
•	Выбрать в блоке «Функции агрегации» - <ins>avg, mах и min</ins>;\
•	Вводить веса критериев или группы критериев с клавиатуры. Для группировки критериев используются скобки из блока «Математические операции»;\
•	Вводить математические операторы и скобки с клавиатуры в дополнение к выпадающим спискам;\
•	Редактировать уже существующую формулу.

**Система должна:**\
•	Автоматически подставить введенные судьей значения критериев в выбранный шаблон формулы;\
•	Рассчитать итоговый балл по выбранному шаблону после закрытия формы и завершения оценивания;\
•	При выборе шаблона «Среднее арифметическое» автоматически определить количество критериев и выполнить деление суммы на их число;\
•	Отображать собираемую формулу в виде читаемого выражения;\
•	Хранить формулу в виде структуры, оперирующей идентификаторами критериев (criterion_id), а не их текстовыми названиями;\
•	Автоматически соблюдать приоритет операций и учитывать скобки.

### Валидация и тестирование формулы
**Организатор должен иметь возможность:**\
•	Запустить тестовый расчёт формулы на демо-данных, введённых вручную.

**Система должна:**\
•	Проверять синтаксическую корректность формулы;\
•	Проверять наличие всех упомянутых в системе критериев в формуле;\
•	Проверять отсутствие деления на ноль (в том числе потенциального, если делитель может оказаться нулевым при некоторых входных данных);\
•	Проверять типы данных;\
•	Запретить сохранение системы оценивания с некорректной формулой.

### Вычисление результатов
**Система должна:**\
•	При закрытии формы организатором автоматически запустить процесс вычисления итоговых баллов по всем участникам категории;\
•	Для каждого участника подставить в формулу числовые значения оценок, выставленных всеми судьями;\
•	Если в категории несколько судей, применить агрегацию их итоговых оценок, согласно варианту, указанному организатором (сумма или среднее);\
•	Округлить итоговый балл до 3 знаков после запятой;\
•	Сохранить итоговый балл и детализацию расчёта и оценок;\
•	Обработать ошибки вычисления (например, деление на ноль) и сообщить организатору о проблемных участниках с указанием причины.

### Просмотр детализации расчёта
**Организатор должен иметь возможность:**\
•	Просмотреть детализацию расчёта итогового балла для любого участника: *какие оценки выставил каждый судья, какие числовые значения были подставлены в формулу*;\
•	Экспортировать детализацию расчёта вместе с итоговым протоколом.

### Управление судьями и доступом
**Организатор должен:**\
•	Добавить хотя бы одного зарегистрированного на платформе пользователя в качестве судьи на каждую категорию.

**Организатор должен иметь возможность:**\
•	Ограничить доступ судьи только определёнными категориями;   
•	Добавлять новых судей из числа зарегистрированных пользователей, вводя их ФИО/логин;\
•	Удалять судей из категорий при условии, что останется минимум 1;\
•	«Открыть форму» для разрешения судьям выставлять и редактировать оценки;\
•	«Закрыть форму» для блокировки возможности редактирования оценок судьями (финализация этапа оценивания).

**Система должна:**\
•	Проверять по совпадению id права доступа при каждой попытке пользователя войти в интерфейс судейства: судья должен быть явно добавлен организатором на конкретный фестиваль для конкретной категории;\
•	Автоматически блокировать возможность редактирования оценок после нажатия организатором кнопки «Закрыть форму»;


## 2. СУДЬЯ
### Доступ и аутентификация
**Судья должен:**\
•	Иметь зарегистрированный аккаунт в системе (базовый пользователь без специальных прав по умолчанию);\
•	Быть явно добавленным организатором на конкретный фестиваль в качестве судьи для получения доступа к оцениванию.

**Судья должен иметь возможность:**\
•	Просматривать список назначенных фестивалей и категорий в личном кабинете.

**Система должна:**\
•	Проверять наличие права судьи на конкретный фестиваль при попытке доступа к интерфейсу оценивания;\
•	Отображать только те категории, к которым судья был привязан организатором;\
•	Запретить доступ к формам оценивания других фестивалей, где пользователь не назначен судьёй.

### Процесс оценивания
**Судья должен:**\
•	Заполнить форму оценивания для каждого участника в назначенной категории;\
•	Отправить итоговые оценки по участнику после заполнения всех критериев формы.

**Судья должен иметь возможность:**\
•	Отредактировать оценки по участника до закрытия формы организатором;\
•	Добавить текстовый комментарий к оценке (если организатор предусмотрел такое поле в форме);\
•	Просматривать список участников категории с информацией: название номера, ФИО/название команды, тип категории.

**Система должна:**\
•	Автоматически сохранять черновик оценок каждые 30 секунд для предотвращения потери данных;\
•	Изолировать данные судей друг от друга: судья не видит оценки коллег до момента закрытия формы организатором;\
•	Заблокировать возможность редактирования оценок после нажатия организатором кнопки «Закрыть форму».;\
•	Скрывать от судьи числовые значения, соответствующие текстовым вариантам оценок (если такие поля имеются);\
•	Сохранять в базе данных числовое значение выбранного варианта в соответствующем поле.

## 3. УЧАСТНИК  
*Полномочия, реализуемые в рамках mvp*
### Просмотр результатов
**Участник должен иметь возможность:**\
•	Найти свои результаты через публичную страницу фестиваля или протокол по поиску (название номера, ФИО, название команды);\
•	Просмотреть итоговый балл и занятое место в категории;\
•	Просмотреть детализацию оценок по критериям и судьям(если организатор разрешил публичный доступ к детальным данным).

**Система должна:**\
•	Предоставить поиск и сортировку по протоколу фестиваля;\
•	Отображать только те данные, которые организатор сделал публичными для данного фестиваля.

### История посещенных фестивалей
**Участник должен:**\
•	Быть зарегистрированным на платформе;\
•	При регистрации ввести свое ФИО, логин и пароль.

**Участник должен иметь возможность:**\
•	Отметить себя как участника конкретного фестиваля;\
•	Заходить в профиль с использованием логина и пароля;\
•	Просматривать в профиле список посещенных им фестивалей и переходить на их страницы для просмотра протоколов;\
•	Удалять отметку об участии;\
•	Фильтровать фестивали в списке по дате проведения и названию.

**Система должна:**\
•	Открывать возможность отметки на фестивале только зарегистрированным пользователям;\
•	При отметке помещать ссылку на страницу фестиваля в профиль пользователя;\
•	При удалении отметки – удалять ссылку.

## 4. НЕЗАРЕГИСТРИРОВАННЫЙ ПОЛЬЗОВАТЕЛЬ (ГОСТЬ)
**Незарегистрированный пользователь (гость) должен иметь возможность:**\
•	Просматривать список активных фестивалей с базовой информацией;\
•	Просматривать публичные итоговые протоколы в объёме, разрешённом организатором *(только итоговые места и баллы без детализации, если не разрешено иное)*;\
•	Выполнять базовую фильтрацию результатов по категориям;\
•	Выполнять базовую сортировку по месту и имени.

**Система должна** отображать сообщения об ошибках в текстовом формате для информирования пользователя.
